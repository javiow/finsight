# oncall-autopilot: 유저 응대 초안 + 운영 Q&A

목표는 "그럴듯한 답"이 아니라 "확인한 것만 말하는 답"이다. 근거가 없으면 답을 지어내지 말고 "확인 필요"라고 쓴다.

## 0. 안전 경계 (절대 어기지 않는다)

- **DB는 조회만 한다.** Supabase MCP는 이미 `read_only=true`로 잠겨 있지만([[supabase_mcp_readonly]] 참고), 쓰기로 보이는 MCP 도구는 애초에 호출하지 않는다.
- **유저에게 나가는 답변은 항상 "🟡 DRAFT — 사람 승인 필요"로 시작한다.** 이 스킬은 어디에도 스스로 전송·게시하지 않는다(이메일 발송, Discord/Slack 포스팅, DB 갱신 등). 산출물은 사람이 검토 후 실제 채널에 그대로 또는 고쳐서 옮기는 텍스트일 뿐이다. 지금은 실제 채널 연동 자체가 없다 — 로컬 one-shot 시연이다(4번).
- **확인되지 않은 사실은 쓰지 않는다.** 모든 문장은 소스(파일:라인, PostHog 이벤트, 실행한 SQL과 결과 요약)로 뒷받침되어야 한다. 뒷받침이 안 되면 "확인 필요: ..."로 명시한다.
- **원본 PII를 그대로 인용하지 않는다.** 카드번호, 거래 원본 행, 다른 유저의 데이터를 답변 텍스트에 넣지 않는다 — 필요한 최소 정보(플랜명, 상태값, 날짜)만 쓴다. `docs/ARCHITECTURE.md`의 LLM 전송 경계 원칙과 같은 이유다.
- **쓰기 액션은 실행하지 않고 에스컬레이션한다.** 구독 해지·환불·플랜 변경·계정 삭제·데이터 수정 요청이 들어오면 직접 처리하지 않고 3-C 형식으로 사람에게 넘긴다.

## 1. 오디언스 판별

입력 텍스트로 둘 중 하나로 분류한다:

- **유저 응대**: 최종 유저가 겪은 에러/문의를 사람이 대신 붙여넣은 경우("이 에러 유저한테 뭐라고 답하지", 에러 스택이나 유저 문의 원문 등). 산출물은 3-A.
- **내부 팀 질문**: 운영 동료가 시스템 상태·원인·통계를 묻는 경우("오늘 에러 뭐가 제일 많이 터졌어", "이 유저 왜 Free로 보여"). 산출물은 3-B.

애매하면 넘겨짚지 말고 `AskUserQuestion`으로 확인한다 — 오디언스를 잘못 짚으면 톤과 승인 게이트 요구사항이 완전히 달라진다.

## 2. 근거 수집

가능한 소스를 확인하고, 실제로 답변에 쓴 것만 인용한다. 조회했지만 관련 없으면 언급하지 않는다.

### 2-1. 코드베이스

`Grep`/`Read`로 에러 메시지 문자열, `src/types/api.ts`의 에러 코드, 관련 기능의 실제 동작을 확인한다. 로그 문구만 보고 추측하지 않는다 — 실제로 그 코드 경로를 열어본다.

### 2-2. 로그·에러 트래킹 (PostHog)

`mcp__posthog__exec`의 `error-tracking`/`logs` 커맨드로 실제 발생 이력을 조회한다(정확한 커맨드 문법은 호출 시점에 `exec` 툴의 `command` 파라미터 설명에서 확인한다). 빈도, 최근 발생 시각, 스택트레이스, 영향받은 유저 수를 근거로 쓴다. 결과가 없으면 "PostHog에서 해당 이벤트를 찾지 못함"이라고 명시한다 — 있었을 거라고 추정하지 않는다.

### 2-3. DB (Supabase, read-only)

1. `mcp__supabase__get_project`로 프로젝트(`kdseyvubflrknmlnshag`, finsight) 상태를 먼저 확인한다.
2. **미인증 상태**(`mcp__supabase__authenticate`가 필요)면 자동으로 OAuth를 시작하지 않는다 — `AskUserQuestion`으로 "지금 Supabase 인증하고 DB 근거까지 확인할까요, DB 근거 없이 진행할까요?"를 물은 뒤 그 선택을 따른다.
3. 프로젝트가 `INACTIVE`(일시정지)면 **조용히 재개하지 않는다**(`db-health` 스킬과 동일 원칙) — 재개는 먼저 승인을 받는다.
4. 조회는 답변에 필요한 최소 컬럼만 `execute_sql`로 읽는다(예: 특정 유저의 플랜·상태·최근 업로드 시각). 테이블 전체 덤프나 무관한 유저 행을 끌어오지 않는다.
5. 미인증·일시정지·조회 실패 중 하나라도 해당하면 최종 답변에 "DB 근거: 확인 불가(원인)"를 명시한다 — 있는 것처럼 쓰지 않는다.

## 3. 출력 형식

### 3-A. 유저 응대 (draft)

```
🟡 DRAFT — 사람 승인 필요, 미전송

[인앱 고객지원 챗 톤 — 1~4문장, 캐주얼하고 짧게, 인사말/서명 없이 본문만]

---
근거:
- <파일:라인 또는 "PostHog: <이벤트 요약>" 또는 "DB: <실행한 조회 내용>">
확인 필요: <근거가 없어 못 채운 부분, 없으면 이 줄 생략>
```

### 3-B. 내부 팀 질문 (direct)

승인 게이트 없이 바로 답한다. 동료에게 터미널로 답하듯 짧고 직접적으로 쓴다. 각 주장 옆에 근거를 인라인으로 붙인다(예: "Free 플랜 3건/24h 제한에 걸렸음 — `src/lib/plan.ts`, PostHog 최근 1시간 동일 유저 429 12건").

### 3-C. ESCALATION (필요시 3-A/3-B 어디에든 추가)

```
⚠️ ESCALATION 필요
무엇: <사람이 수동으로 해야 하는 행동 — 구독 해지, 환불, 데이터 수정 등>
왜 자동화하지 않았는가: DB read-only + 계정 변경은 사람 판단 필요
```

## 4. 로컬 one-shot 실행

지금은 always-on 입구(웹훅, 봇, 알림 트리거)가 없다. 사람이 이 스킬을 직접 호출하며 에러 메시지·유저 문의·운영 질문 텍스트를 프롬프트나 파일로 준다. 상시 채널 연동은 범위 밖이며, 이 스킬의 답변 품질이 검증된 뒤 별도로 설계한다.

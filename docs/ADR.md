# Architecture Decision Records

## 철학

**MVP 프로토타입이다. 지금 없는 위협을 방어하지 않는다.**

공격자와 사용자 베이스를 전제로 하는 방어는 그 둘이 생겼을 때 넣는다. 대신 **한 번 잘못 만들면 되돌리기 어려운 것** — 데이터 모델, 접근 제어, 실패 처리 경계, API 계약 — 은 처음부터 제대로 만든다.

작동하는 최소 구현을 선택하되, 실패 모드는 격리한다. 행 하나가 깨져 명세서 전체를 실패시키거나, 배치 하나가 실패해 앞선 배치를 날리는 설계는 최소 구현이 아니라 미완성이다.

---

### ADR-001: Supabase 올인원
**결정**: Auth · Postgres · Storage · RLS를 Supabase 하나로 쓴다.
**이유**: 금융 데이터의 행 단위 격리(RLS)가 기본으로 따라온다. 인증·DB·파일 저장을 별도 벤더로 조합하면 사용자 삭제 시 세 곳을 각각 정리해야 한다.
**트레이드오프**: 벤더 종속. Postgres 자체는 이식 가능하지만 Auth와 Storage는 아니다.

### ADR-002: 읽기는 Server Component, 변경은 `app/api/`
**결정**: 조회는 Server Component에서 RLS가 걸린 클라이언트로 직접 수행하고, 모든 변경과 외부 API 호출은 `app/api/` 라우트 핸들러가 소유한다. 브라우저 `authenticated` 역할에서는 INSERT/UPDATE/DELETE를 revoke한다.
**이유**: 조회까지 API로 우회시키면 모든 페이지가 빈 껍데기로 뜨고, 월 1회 방문하는 사용자에게 대시보드 체감 속도가 나빠진다. 반대로 변경을 클라이언트에 열면 RLS만으로는 도메인 규칙(플랜 게이팅, 한도, 순서)을 걸 수 없다.
**트레이드오프**: 규칙이 두 갈래라 "이건 어디서 하나"를 매번 판단해야 한다. DB 권한으로 강제해 실수를 컴파일 타임 대신 런타임에서라도 잡는다.

### ADR-003: 파싱 파이프라인을 단계로 나누고 lease로 직렬화
**결정**: 업로드(`POST /api/statements`)와 분류(`POST .../classify` 배치 반복)를 분리하고, 분류는 statement 단위 lease를 얻은 요청만 수행한다.
**이유**: 한 방 요청은 Vercel 300초 안에는 들어가지만 90초 동안 스피너만 돌고, 7번째 배치에서 실패하면 앞의 6개가 통째로 날아간다. 배치 커밋 + lease면 진행률을 그릴 수 있고, 새로고침·동시 탭·서버 재시작에서 안전하게 재개된다.
**트레이드오프**: 라우트가 늘고 클라이언트가 폴링 루프를 관리해야 한다. lease 만료 시간(90초) 튜닝이 필요하다.

### ADR-004: LLM에 원본을 보내지 않는다 — denylist + 형태 요약
**결정**: LLM #1에는 헤더와 비식별화된 최대 20행만 보낸다. 식별정보는 헤더 키워드와 값 패턴 denylist로 마스킹하고, **denylist에 걸리지 않았지만 날짜·금액·가맹점 후보로도 분류되지 않은 컬럼은 값 대신 형태 요약**(`숫자 8자리`, `YYYY.MM.DD 형태` 등 고정 어휘)만 보낸다.
**이유**: 프라이버시 거부감이 가입 전환의 1차 장벽이라 "원본을 안 보낸다"가 제품 약속이다. 그렇다고 판별 안 된 컬럼을 통째로 가리면 — allowlist 방식 — 카드사 포맷의 다양성을 LLM으로 흡수한다는 설계 자체가 무너진다. 휴리스틱이 못 알아본 컬럼이 곧 LLM이 풀어야 할 문제이기 때문이다. 형태만 보내면 LLM은 컬럼 성격을 판단할 수 있고 실제 값은 나가지 않는다.
**트레이드오프**: `shape` 어휘를 고정 집합으로 관리해야 한다. 자유 문자열로 두면 세션마다 표현이 달라져 LLM #1 프롬프트가 불안정해진다.

### ADR-005: 전역 가맹점 캐시 대신 유저별 캐시
**결정**: `user_merchant_categories` 하나에 LLM 분류 결과와 사용자 수정을 함께 담는다(`source` 컬럼으로 구분). 전 사용자 공유 캐시는 만들지 않는다.
**이유**: 전역 캐시로 아끼는 금액은 사용자 100명 기준 월 3,000원 수준이다. 그 대가로 테이블 하나와 프롬프트 인젝션 방어 일체를 져야 한다 — 가맹점명은 사용자가 CSV로 제어하는 문자열이고, 그게 LLM 프롬프트를 거쳐 공유 상태에 쓰이기 때문이다. 유저별로 두면 인젝션이 나도 자기 데이터만 오염된다. 같은 사용자의 재업로드·다음 달 히트는 그대로 얻는다.
**트레이드오프**: 사용자가 늘면 같은 가맹점을 여러 번 분류한다. LLM 비용이 눈에 보이기 시작하면 전역 캐시를 인젝션 방어와 함께 다시 넣는다.

### ADR-006: 사용자 수정은 캐시에 남긴다
**결정**: 카테고리 수정 결과를 거래 행이 아니라 `user_merchant_categories`에 `source='user'`로 저장하고, LLM 결과 upsert는 `WHERE source='ai'` 조건을 건다.
**이유**: 수정을 거래 행에만 남기면 다음 달 명세서에서 같은 오분류가 반복된다. AI 분류는 반드시 틀리므로, 고친 게 유지되지 않으면 사용자가 떠난다.
**트레이드오프**: 사용자가 한 번 잘못 고치면 계속 잘못 분류된다. 되돌리려면 같은 가맹점을 다시 고쳐야 한다.

### ADR-007: 결제 상태의 진실 원천은 웹훅
**결정**: `profiles.plan`은 Polar 웹훅으로만 갱신한다. successUrl 리디렉트로는 올리지 않는다. `customerExternalId`는 `/api/checkout`에서 세션 값을 서버가 강제 주입하고 클라이언트가 보낸 값은 폐기한다.
**이유**: 리디렉트 URL은 사용자가 직접 칠 수 있고, Polar adapter는 `customerExternalId`를 쿼리 파라미터에서 읽으므로 그대로 두면 브라우저에서 값을 바꿔 남의 계정을 Pro로 만들 수 있다.
**트레이드오프**: 웹훅이 늦으면 결제 직후 잠깐 Free로 보인다. "결제 확인 중" 배너와 2분 타임아웃 안내로 덮는다.

### ADR-008: 계정 삭제는 재시도 가능한 상태 머신
**결정**: `deletion_status`(`active`/`pending`/`failed`)를 두고 **Polar 구독 취소 확인 → Storage 잔여 0 확인 → `auth.users` 삭제** 순으로만 진행한다. 앞 단계가 실패하면 `failed`로 남기고 `auth.users`를 지우지 않는다.
**이유**: "실패해도 다음 단계로" 방식은 Polar 취소가 실패했는데 계정을 지워버려 **복구 불가 + 결제 지속**을 만든다. Storage는 DB cascade를 타지 않으므로 순서를 코드가 보장해야 한다.
**트레이드오프**: 삭제가 즉시 끝나지 않고 사용자에게 재시도를 요구할 수 있다. `pending`/`failed` 상태에서는 업로드·체크아웃을 막아야 한다.

### ADR-009: API 계약을 코드보다 먼저 고정
**결정**: `src/types/api.ts`에 요청·응답 타입과 에러 코드 enum, 한국어 메시지 매핑을 먼저 확정하고 이후 모든 구현이 이 파일을 읽는다.
**이유**: 구현이 여러 세션으로 나뉘어 진행되므로 앞선 세션의 응답 형태를 뒤 세션이 볼 수 없다. 필드명을 지어내도 빌드는 통과해 자동 검증에 안 걸린다. 에러 코드 매핑은 덤이 아니라 "파싱 실패"만 띄우면 사용자가 재시도조차 못 하는 문제의 해법이다.
**트레이드오프**: 계약을 바꾸려면 여러 파일을 함께 고쳐야 한다.

### ADR-010: 남용 방지는 콘솔 지출 한도 + 최소 요청 한도
**결정**: 사용량 집계 테이블을 만들지 않는다. Anthropic 콘솔의 월 지출 한도를 손실 상한으로 두고, 앱에서는 기존 `statements.created_at`을 세어 24시간 Free 3건 / Pro 10건과 동시 처리 1건만 검사한다.
**이유**: 콘솔 한도는 손실 상한이고 앱 한도는 정상 사용자의 가용성을 지킨다. 별도 카운터 테이블은 갱신 지점이 여러 곳으로 흩어져 동기화 버그를 부른다.
**트레이드오프**: 세밀한 사용량 리포트가 없다. 요금제별 정액 한도를 팔려면 그때 집계 테이블을 넣는다.

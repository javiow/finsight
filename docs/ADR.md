# Architecture Decision Records

## 철학

**포트폴리오/데모 MVP다. 지금 없는 위협을 방어하지 않는다.**

공격자와 사용자 베이스를 전제로 하는 방어는 그 둘이 생겼을 때 넣는다. 락·상태 머신·집계 인프라는 규모가 만들어내는 문제의 해법인데, 지금은 그 규모가 없다.

대신 **한 번 잘못 만들면 되돌리기 어려운 것** — 데이터 모델, 접근 제어, LLM 전송 경계, API 계약 — 은 처음부터 제대로 만든다. 그리고 실패는 격리한다. 행 하나가 깨져 명세서 전체를 실패시키는 설계는 최소 구현이 아니라 미완성이다.

---

### ADR-001: Supabase 올인원
**결정**: Auth · Postgres · Storage · RLS를 Supabase 하나로 쓴다.
**이유**: 금융 데이터의 행 단위 격리(RLS)가 기본으로 따라온다. 인증·DB·파일 저장을 별도 벤더로 조합할 이유가 없다.
**트레이드오프**: 벤더 종속. Postgres 자체는 이식 가능하지만 Auth와 Storage는 아니다.

### ADR-002: 읽기는 Server Component, 변경은 `app/api/`
**결정**: 조회는 Server Component에서 RLS가 걸린 클라이언트로 직접 수행하고, 모든 변경과 외부 API 호출은 `app/api/` 라우트 핸들러가 소유한다. 브라우저 `authenticated` 역할에서는 INSERT/UPDATE/DELETE를 revoke한다.
**이유**: 조회까지 API로 우회시키면 모든 페이지가 빈 껍데기로 뜬다. 반대로 변경을 클라이언트에 열면 RLS만으로는 도메인 규칙(플랜 게이팅, 한도)을 걸 수 없다. revoke는 SQL 두 줄이고, "변경은 API를 거친다"를 규율이 아니라 DB 권한으로 만든다.
**트레이드오프**: 규칙이 두 갈래라 "이건 어디서 하나"를 판단해야 한다.

### ADR-003: 업로드와 분류를 두 요청으로 나눈다 (락 없이)
**결정**: `POST /api/statements`(파싱·저장)와 `POST /api/statements/:id/classify`(분류)를 나누고, 클라이언트가 `pending`이 0이 될 때까지 후자를 반복 호출한다.
**이유**: 한 요청에 다 넣으면 사용자가 60초 넘게 스피너만 본다. 나누면 진행률을 그릴 수 있고, 배치마다 커밋되므로 중간에 실패해도 앞선 배치는 남는다.
**락을 두지 않는 이유**: 분류는 `category IS NULL`인 행만 집으므로 요청이 겹쳐도 결과가 깨지지 않는다. 최악이 같은 가맹점을 두 번 분류하는 것이고 그마저 ADR-005 캐시가 대부분 흡수한다. lease 토큰과 만료 시간 튜닝은 이 리스크에 비해 비싸다.
**트레이드오프**: 두 탭을 동시에 열면 LLM 호출이 몇 번 중복될 수 있다. 사용자당 월 1회 업로드에서는 무시할 수준이다.

### ADR-004: LLM에 원본을 보내지 않는다 — denylist + 형태 요약
**결정**: LLM #1에는 헤더와 비식별화된 최대 20행만 보낸다. 식별정보는 헤더 키워드와 값 패턴 denylist로 마스킹하고, denylist에 걸리지 않았지만 날짜·금액·가맹점 후보로도 분류되지 않은 컬럼은 값 대신 **형태 요약**만 보낸다. 어휘는 `숫자` · `날짜형` · `문자열` · `빈값` 넷으로 고정한다.
**이유**: 프라이버시 거부감이 가입 전환의 1차 장벽이라 "원본을 안 보낸다"가 제품 약속이다. 그렇다고 판별 안 된 컬럼을 통째로 가리면(allowlist 방식) 카드사 포맷의 다양성을 LLM으로 흡수한다는 설계가 무너진다 — 휴리스틱이 못 알아본 컬럼이 곧 LLM이 풀어야 할 문제이기 때문이다. 형태만 보내면 LLM은 컬럼 성격을 판단할 수 있고 실제 값은 나가지 않는다.
**트레이드오프**: 어휘를 넷으로 줄여 표현력을 포기했다. 자유 문자열로 두면 세션마다 표현이 달라져 프롬프트가 불안정해지므로, 늘리더라도 고정 집합은 유지한다.

### ADR-005: 전역 가맹점 캐시 대신 유저별 캐시
**결정**: `user_merchant_categories` 하나에 LLM 분류 결과와 사용자 수정을 함께 담는다(`source` 컬럼으로 구분). 전 사용자 공유 캐시는 만들지 않는다.
**이유**: 전역 캐시로 아끼는 금액은 사용자 100명 기준 월 3,000원 수준이다. 그 대가로 프롬프트 인젝션 방어 일체를 져야 한다 — 가맹점명은 사용자가 CSV로 제어하는 문자열이고, 그게 LLM 프롬프트를 거쳐 공유 상태에 쓰이기 때문이다. 유저별로 두면 인젝션이 나도 자기 데이터만 오염된다. 같은 사용자의 재업로드·다음 달 히트는 그대로 얻는다.
**트레이드오프**: 사용자가 늘면 같은 가맹점을 여러 번 분류한다. LLM 비용이 눈에 보이면 전역 캐시를 인젝션 방어와 함께 다시 넣는다.

### ADR-006: 사용자 수정은 캐시에 남긴다
**결정**: 카테고리 수정 결과를 거래 행이 아니라 `user_merchant_categories`에 `source='user'`로 저장하고, LLM 결과 upsert는 `WHERE source='ai'` 조건을 건다.
**이유**: 수정을 거래 행에만 남기면 다음 달 명세서에서 같은 오분류가 반복된다. AI 분류는 반드시 틀리므로, 고친 게 유지되지 않으면 사용자가 떠난다.
**트레이드오프**: 사용자가 한 번 잘못 고치면 계속 잘못 분류된다. 되돌리려면 같은 가맹점을 다시 고쳐야 한다.

### ADR-007: 결제 상태의 진실 원천은 웹훅
**결정**: `profiles.plan`은 Polar 웹훅으로만 갱신한다. successUrl 리디렉트로는 올리지 않는다. `customerExternalId`는 `/api/checkout`에서 세션 값을 서버가 강제 주입하고 클라이언트가 보낸 값은 폐기한다.
**이유**: 리디렉트 URL은 사용자가 직접 칠 수 있고, Polar adapter는 `customerExternalId`를 쿼리 파라미터에서 읽으므로 그대로 두면 브라우저에서 값을 바꿔 남의 계정을 Pro로 만들 수 있다.
**멱등 처리**: 이벤트 ID 테이블을 두지 않는다. 갱신을 `WHERE modified_at < :eventModifiedAt`로 걸면 재전송은 자연히 no-op이 되고, 순서가 뒤바뀐 이벤트도 같은 조건으로 걸러진다. 테이블 하나와 정리 정책이 사라진다.
**트레이드오프**: 웹훅이 늦으면 결제 직후 잠깐 Free로 보인다. "결제 확인 중" 배너와 2분 타임아웃 안내로 덮는다.

### ADR-008: API 계약을 코드보다 먼저 고정
**결정**: `src/types/api.ts`에 요청·응답 타입과 에러 코드 enum, 한국어 메시지 매핑을 먼저 확정하고 이후 모든 구현이 이 파일을 읽는다.
**이유**: 구현이 여러 세션으로 나뉘어 진행되므로 앞선 세션의 응답 형태를 뒤 세션이 볼 수 없다. 필드명을 지어내도 빌드는 통과해 자동 검증에 안 걸린다. 에러 코드 매핑은 덤이 아니라 "파싱 실패"만 띄우면 사용자가 재시도조차 못 하는 문제의 해법이다.
**트레이드오프**: 계약을 바꾸려면 여러 파일을 함께 고쳐야 한다.

### ADR-009: 남용 방지는 콘솔 지출 한도 + 요청 건수 제한
**결정**: 사용량 집계 테이블을 만들지 않는다. Anthropic 콘솔의 월 지출 한도를 손실 상한으로 두고, 앱에서는 기존 `statements.created_at`을 세어 24시간 Free 3건 / Pro 10건만 검사한다.
**이유**: 콘솔 한도는 손실 상한이고 앱 한도는 정상 사용자의 가용성을 지킨다. 별도 카운터 테이블은 갱신 지점이 흩어져 동기화 버그를 부른다.
**트레이드오프**: 세밀한 사용량 리포트가 없다. 요금제별 정액 한도를 팔려면 그때 집계 테이블을 넣는다.
**주의**: 콘솔 지출 한도는 코드가 아니라 수동 설정이다. 설정하지 않으면 이 방어의 절반이 없으므로 배포 체크리스트에 남긴다.

### ADR-010: 모든 LLM 호출에 `claude-opus-5`
**결정**: 매핑·분류·인사이트 모두 `claude-opus-5`. 모델 ID는 `src/services/claude.ts`의 상수 하나로 둔다. 판단이 얕은 매핑·분류에는 `output_config: {effort: "low"}`를 준다.
**이유**: 모델을 둘로 나누면 클라이언트 초기화·에러 처리·재시도 로직이 두 벌이 된다. 캐시(ADR-005)가 반복 호출을 이미 제거해 저렴한 모델로 얻는 실질 절감이 작다.
**트레이드오프**: 트래픽이 커지면 매핑·분류를 저렴한 모델로 내리는 게 맞다. 상수 하나라 교체는 한 줄이다.
**API 제약** (Opus 5 기준, 구현 시 반드시 반영):
- **thinking이 기본 ON이다** (Opus 4.8/4.7과 반대). 생략하면 adaptive로 동작하고 thinking 토큰도 출력으로 과금된다.
- **`max_tokens`는 thinking + 응답의 합계 상한이다.** 넉넉히 잡지 않으면 응답이 조용히 잘린다.
- 큰 `max_tokens`로 비스트리밍 호출하면 SDK HTTP 타임아웃에 걸린다. 인사이트 호출은 **스트리밍**으로 처리한다.
- structured outputs(`output_config: {format: {type: "json_schema", schema}}`)는 **citations와 병용 불가**다(400).

### ADR-011: 포트폴리오/데모 — Polar 샌드박스만 사용
**결정**: 실결제를 받지 않는다. Polar는 샌드박스 환경(`sandbox-api.polar.sh`)으로만 붙이고, 랜딩에 테스트 카드 번호를 안내한다.
**이유**: 한국에서 실결제를 붙이려면 사업자등록과 PG 심사가 선행되며, 이는 코드로 자동화할 수 없는 블로커다. 결제 레이어를 실서비스와 동일하게 구현해두면 전환은 키 교체로 끝난다. 웹훅 서명 검증은 `@polar-sh/nextjs`가 내부 처리하므로 직접 짜지 않는다.
**이 결정이 없애주는 것**: 실제 돈이 오가지 않으므로 "취소 실패인데 계정이 지워져 결제가 계속된다" 류의 시나리오를 방어할 필요가 없다. 계정 삭제를 MVP에서 뺀 근거다(PRD 참조).
**트레이드오프**: 실제 매출 검증이 불가능하다. 실서비스 전환 시 개인정보 처리방침·데이터 파기정책과 계정 삭제 흐름을 함께 갖춰야 한다.
